很多工作看起来是“每天都不一样”，但做久了就会发现，真正反复出现的部分其实很多。

比如：

- 新项目接手时先看哪些文件
- 排查 bug 时先问哪些问题
- 写技术方案时先列哪些章节
- 发布前要做哪些检查

如果每次都从空白开始，其实是在重复支付同样的思考成本。更好的做法，是把这些步骤慢慢沉淀成可复用的 skill。

## Skill 的本质是什么

我更愿意把 skill 理解成一种“能被重复调用的方法单元”。

它通常包含四个部分：

- 目标：这套方法是为了解决什么问题
- 输入：需要哪些上下文和材料
- 过程：按什么顺序完成
- 输出：最后应该得到什么结果

只要这四部分是相对稳定的，这件事就有机会被沉淀成 skill。

## 从哪里开始抽象

最好的起点，不是挑最复杂的任务，而是挑最常重复的小任务。

因为复杂任务往往变量太多，抽象起来容易失真；而高频小任务边界清晰、反馈快，更适合练习方法沉淀。

几个典型例子：

- 写日报或周报
- 新仓库代码巡检
- bug 初步定位
- PR 自查
- 部署前检查

这些工作如果做得足够多，就一定能总结出稳定模式。

## 一个好 Skill 应该具备什么特征

### 1. 边界清楚

好的 skill 不追求无所不能，而是能清楚回答“它负责什么，不负责什么”。

边界一模糊，执行时就会不断分叉，最后又退回到临场发挥。

### 2. 步骤足够具体

“先分析一下问题”不叫步骤。

真正有用的步骤应该是能被执行的，比如：

1. 读取错误日志的前后 30 行
2. 对比最近一次可用版本与当前版本差异
3. 先验证配置，再验证代码

越具体，越容易复用。

### 3. 输出可检查

如果一个 skill 结束后，你很难判断结果是不是合格，那它通常还不够成熟。

比如代码 review skill 的输出，可以明确成：

- 风险点列表
- 影响范围判断
- 是否需要补测试

这样结果就更容易被检查，也更容易被团队复用。

## Skill 不是一次性写出来的

真正好用的 skill 通常不是设计出来的，而是迭代出来的。

一个比较自然的演化方式是：

1. 先完整做一次
2. 再记录关键步骤
3. 然后删除无效动作
4. 最后补上检查项和输出格式

经过几轮之后，这套方法才会越来越像一个真正可调用的 skill。

## 常见误区

### 误区一：一开始就想做得很大

很多人会试图设计一个覆盖所有场景的万能 skill，结果就是太重、太抽象、谁也不想用。

与其追求完整，不如先追求可用。

### 误区二：只写步骤，不写判断条件

步骤很重要，但什么时候跳过、什么时候停止、什么时候升级处理，同样重要。

没有判断条件的 skill，执行时仍然会卡住。

### 误区三：只管产出，不管验证

如果没有最后的检查动作，skill 很容易变成流水账。方法能重复，不代表结果就可靠。

## 一套最小可用模板

当我准备把一项工作沉淀成 skill 时，通常会先写一个最小模板：

```text
Skill 名称：
目标：
适用场景：
输入材料：
执行步骤：
输出格式：
检查清单：
```

这个模板不复杂，但已经足够让一件重复工作从“靠感觉完成”变成“按方法完成”。

## 结语

沉淀 skill 的价值，不只是让自己做得更快。

更重要的是，它会把很多本来依赖经验和状态的事情，慢慢变成更稳定的系统。这样一来，效率会提高，协作会更顺，长期积累也会更容易。
